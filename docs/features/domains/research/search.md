## dreamhost-facts

SUMMARY
DreamHost's own domain search is a plain availability checker (panel "Find New Domains" page + public dreamhost.com/domains search) with no documented AI suggestions inside search itself; their AI naming play is a separate free "Business Name Generator" tool (keywords + industry -> names -> real-time domain check -> register on the spot). Transfers-in cost $9.99 for .com, always include a 1-year extension, take ~5-7 business days after unlock + EPP code entry, cannot move DNS records, and are blocked by ICANN's 60-day lock after registration, after a prior transfer, or after any registrant-info/privacy change. For domains staying at an outside registrar, DreamHost's documented pattern is "Host a domain at DreamHost if it is registered at another company": point nameservers ns1/ns2/ns3.dreamhost.com (recommended) or individual A records; there is zero Domain Connect support (absent from help site and from domainconnect.org's provider list). Pricing in search results shows promo first-year vs higher renewal (.com $9.99/$19.99; .shop $0.99/$34.99; .online $1.99/$29.95), and DreamHost explicitly does NOT sell premium domains. Bonus finding: the public search is powered by marketing-api-aws.dreamhost.io (cmd=domreg-availability) behind a reCAPTCHA score gate, and its error state reads "Something went wrong! Please try your search again, or contact support for assistance."

RECOMMENDATIONS
- Treat 'connect without transfer' as a first-class outcome of the universal field: DreamHost's own docs call transfer optional and recommend nameserver pointing (ns1-3.dreamhost.com) as the default for externally registered domains — Remixer should generate the exact 3 nameserver values and set expectations with DreamHost's own 4-72h propagation language.
- Never route a novice to transfer as the default for an external domain: it takes 5-7 business days, requires unlock + EPP code at the other registrar, is blocked by the 60-day lock (new registrations, recent transfers, or any registrant/privacy change), and can't even be started for .AM/.AT/.BZ/.FM/.JP/.NGO/.ONG/.OOO/.PLACE/.WS — offer it as an optional 'move it later, $9.99 includes an extra year' upsell after the site is connected via nameservers.
- For domains the user registers THROUGH Remixer, remember they land in the same account, so no connect step should be shown at all — DreamHost docs confirm nameservers are configured automatically for DreamHost-registered domains; the domain is usable in ~15 minutes (registration) with up to 24-72h DNS settle.
- Show both prices in search results the way DreamHost's own table does (Register vs Renew): the deltas are large (.shop $0.99 -> $34.99, .online $1.99 -> $29.95, .me $2.99 -> $32.95) and DreamHost already normalizes 'first year promo, renews higher' language; hiding renewal prices would be off-brand and a dark pattern.
- No premium/aftermarket states are needed: DreamHost verifiably does not sell premium domains and has no brokerage, so a taken .com should pivot straight to AI alternatives and other TLDs — never 'make an offer' or aftermarket pricing.
- Don't design around Domain Connect: DreamHost supports it in no direction, so the external-registrar path must be hand-held manual instructions (per-registrar 'where to paste the nameservers' guidance would be a genuine differentiator for novices).
- Reuse the existing AI-suggestion precedent: the Business Name Generator's pattern (keywords/industry -> generated names -> real-time availability -> register on the spot) is already DreamHost-blessed; Remixer's advantage is it already knows the site prompt, so it can skip the input step entirely.
- Mind the reCAPTCHA-gated availability API (marketing-api-aws.dreamhost.io, cmd=domreg-availability): the in-builder search needs an authenticated/panel-side availability endpoint or the same bot-gating will surface 'Something went wrong!' errors to real users; also design a graceful degraded state — DreamHost's current public error card is a dead end with no retry affordance.
- If Remixer registers a new domain and the user later asks to move it elsewhere, surface the ICANN 60-day lock proactively at registration time (one quiet line), since DreamHost policy triggers it even on privacy-setting changes; the panel's 'Opt Out of 60-Day Transfer Lock' toggle exists but only for outbound flow.
- Warn (or auto-handle) the DNS-records gap when connecting an external domain via nameservers: DreamHost docs stress that existing custom records (e.g., the user's Google Workspace email MX at GoDaddy) stop working unless recreated in the DreamHost panel first — a novice-safe flow should detect existing MX records and offer to copy them before switching.

## competitor-search-ux

SUMMARY
Across all 10 competitors, the domain results screen follows one dominant pattern: an exact-match hero card with a badge ("Exact match" at Squarespace/Wix/Hostinger, "GREAT NAME" at GoDaddy), heavily discounted first-year pricing shown as a strikethrough (regular price crossed out, promo price large), and a distinct hero CTA ("Make It Yours" at Wix/GoDaddy/Hostinger) that differs from the list-row CTA ("Get It"/"Get it"/"Buy"/"Select"). Taken domains get a one-line friendly message ("X is already registered. Explore some great alternatives below." / "X is already taken. We found a great alternative just for you!") followed immediately by alternatives; only GoDaddy monetizes the taken state with brokerage ("Hire a Broker", $99.99 fee) and aftermarket "Minimum Offer" premiums — Squarespace, Wix, Hostinger, Shopify and all AI builders simply show alternatives. No platform auto-detects "I already own this domain" inside the search field: every one exposes a separate, explicit entry point next to or before search ("Use a Domain I Own", "Connect existing domain", "On a domain I already own", "Connect a domain you own", "Connect domain", "Already have a domain? Transfer to Wix today."). AI-native builders (Lovable, Durable, 10Web, Shopify with AI suggestions, GoDaddy Airo) add generated name suggestions, and the newest pattern (Lovable, Shopify, Wix) is Entri/automatic provider detection for connecting external domains after the user picks the connect path.

RECOMMENDATIONS
- Use the industry-standard results anatomy novices already recognize: an exact-match hero card with an 'Exact match'/'Available' badge, first-year price large with renewal struck-through context ($9.99 first year, renews $19.99 — DreamHost can show BOTH numbers inline, which is more honest than GoDaddy/Hostinger hiding renewal behind multi-year-term footnotes), then a single scrolling alternatives list with a load-more control.
- Differentiate hero CTA from row CTA like Wix/GoDaddy/Hostinger do ('Make It Yours' on hero vs 'Get It' on rows) — but for novices, a plainer verb pair works: e.g. 'Get this domain' on the hero and 'Get' on rows; avoid 'Buy' alone (only Shopify uses it) and avoid cart-icon-only CTAs (Squarespace's weakest pattern).
- For the taken state, copy Hostinger/Wix's tone, not GoDaddy's: one friendly line ('name.com is already taken — here are some great alternatives') followed immediately by AI-relevant alternatives. Since DreamHost has no brokerage, never show 'make an offer'/'Hire a Broker' — GoDaddy is the only competitor that monetizes this state and it reads as an upsell trap; Squarespace's bare 'unavailable' tag is the other extreme (dead end without guidance).
- Keep 'I already own a domain' as an explicit, always-visible secondary entry next to the search field (like Wix's 'Already have a domain? Transfer to Wix today.' one-liner under the search box) — no competitor auto-detects ownership in the field, BUT Remixer can leapfrog: since typing an exact registered domain in the buy search is a strong signal, detect it and inline-offer 'Own this domain? Connect it instead' on the taken result (no one does this today; Lovable's Entri auto-detection only kicks in after the user picks Connect).
- Split the connect path by registrar like the best-in-class flows: domain registered at DreamHost = auto-connect with zero DNS steps (Hostinger and GoDaddy both auto-connect same-registrar domains and novices expect this); external registrar = guided connect, ideally Entri-style provider detection (Lovable, Shopify) with a manual A/TXT-record fallback.
- Lean into AI suggestions as the differentiator inside results, not a separate generator: Shopify labels a section 'AI-powered suggestions', GoDaddy Airo suggests from the business description, and Hostinger injects a contextual line on the hero ('This domain is ideal for a coffee shop or cafe.') — Remixer already knows the site prompt, so it can rank suggestions by the site's actual topic, which only Airo approximates today.
- Adopt badge vocabulary sparingly: 'Exact match' (Squarespace/Wix/Hostinger) and at most one promo badge ('Best deal' Hostinger / 'Recommended' Wix). Avoid GoDaddy's badge soup (GREAT NAME / PROMOTED / PREMIUM / LOVED BY LOCALS / BEST IN CLASS) which erodes trust. Since DreamHost gives free WHOIS privacy forever, steal GoDaddy's single trust line placement: one reassurance sentence directly under the hero ('Every domain includes free WHOIS privacy, forever.').
- If premium/aftermarket domains appear in DreamHost's inventory feed, either filter them out or tag them 'Premium' with the real price like Squarespace ('+ $X one-time fee') — never present them as needing negotiation, since DreamHost has no brokerage.
- Structure the list as: exact-match hero → 4-8 same-name-other-TLD rows → AI name suggestions → 'Show more' (Wix/Hostinger pattern). Hostinger's category filter chips (Popular/Business/...) are overkill for a novice in-builder flow; skip pagination entirely — every competitor uses progressive load.

## ai-suggestions-ux

SUMMARY
Researched how the industry presents AI-generated domain suggestions, with live UI captures of GoDaddy and Squarespace results pages. Two presentation patterns dominate: GoDaddy folds AI names into its single results list, marking each with a purple double-sparkle icon plus a Title Case brand-name heading (no "AI" text label anywhere), while Squarespace runs a separate generator that labels the whole page "Results powered by Squarespace AI" and groups results by brand concept (5 concepts, each with a .com first plus 2 creative-TLD variants) under tone tabs (Neutral/Playful/Professional/Friendly/Informative/Quirky). Every major product asks the user to "describe your business" in plain words rather than enter keywords, and Hostinger Horizons is the strongest builder precedent: it pre-generates domain recommendations "based on your project content" when you hit Connect domain, with suggestions explicitly optional. NN/g research (n=107) found zero users associate the sparkle icon with AI — it must be paired with a text label. Per-name one-line rationales are rare; the industry instead puts the "reason" on the TLD ("Keep your .store open 24/7") or the tone tab. Key anti-patterns documented: $0.01-with-3-year-term and "ONE PER CUSTOMER, renews at $34.98" price bait, walls of weird-TLD spam, aftermarket premium prices mixed into novice flows, and oddly-spelled AI names (80% of consumers avoid oddly spelled domains per GoDaddy's own survey).

RECOMMENDATIONS
- Never use the sparkle icon alone to mark AI suggestions: NN/g's n=107 study found zero users read sparkles as 'AI' (17% think it means favorite/save — deadly next to a heart/favorite control like GoDaddy's). Pair any icon with a plain-language text label.
- The best-tested label pattern is Squarespace's explicit page-level attribution 'Results powered by Squarespace AI' plus plain group headers; for Remixer's novice audience, a benefit-first label like 'Name ideas for your site' with a small 'generated from your site description' subtitle beats the bare word 'AI'.
- Since Remixer already knows the site's prompt, follow the Hostinger Horizons precedent exactly: pre-generate recommendations 'based on your project content' the moment the domain step opens, and keep them explicitly optional ('select a recommended name or type your own') — no other builder (Durable, Mixo, Lovable) verifiably does this from site content, so it is a differentiator.
- Present each AI suggestion as a Title Case brand name above the raw domain (GoDaddy '✦ Ceramics Handmade' / Squarespace 'ClayCup Studio' both do this) — novices cannot parse smushedlowercasewords; showing the readable name first is the industry-converged pattern.
- Structure results as few, grouped concepts (Squarespace: 5 concepts × 3 domains with .com always first) with a 'more ideas'/regenerate action, not a long mixed feed; do NOT interleave AI names with premium aftermarket listings (GoDaddy's $11,395 rows mid-list are the most confusing element for novices, and DreamHost has no brokerage anyway).
- Keep AI suggestions to correctly-spelled real words, two words or fewer: GoDaddy's own survey says 80% of consumers avoid oddly spelled domains, 56% red-flag misspellings, 43% trust correctly spelled full words, 40% trust short names — so suppress dropped-vowel/alternate-spelling generation styles entirely.
- Show honest flat pricing on every suggestion card: DreamHost's $9.99 first year / renews $19.99 / free WHOIS forever is a genuine trust advantage against the documented bait patterns ($0.01 with hidden 3-yr term at GoDaddy; $0.98 'ONE PER CUSTOMER' renewing at $34.98 at Namecheap). Print the renewal price up front — Lovable also discloses 'purchase price and renewal price may differ'.
- Per-name one-line rationales (e.g. 'Perfect for e-commerce and retail') have almost no live industry precedent in search results — the 'reason' is carried by tone tabs (Squarespace) or per-TLD taglines (GoDaddy's '.store — Keep your .store open 24/7'). If Remixer adds per-name reasons, keep them to why-it-fits-your-site ('Combines your craft + what you sell') — this would be novel, not imitation.
- Squarespace's tone filters (Neutral/Playful/Professional/Friendly/Informative/Quirky) are the one refinement control novices understand; a lightweight 'more playful / more professional' regenerate control is worth testing over TLD/length filters.
- Expect and design for AI-suggestion distrust: generated names converge across vendors (same 'Artisan Mug Works' from GoDaddy and Squarespace), can collide with trademarks (NamePros flagged UDRP risk), and mechanical prefix/suffix output labeled 'AI' (Instant Domain Search) reads as spam — cap the list, keep names obviously derived from the user's own description, and always keep the typed-domain path (including 'I already own this') visually primary.

## own-domain-transfer-ux

SUMMARY
Across builders, the "domain I already own" case is handled not on the search-results screen but as a separate, explicitly labeled entry point ("Use a domain I own" — Squarespace; "Connect a domain you already own" — Wix; "Connect existing domain" — Shopify admin; "Add a domain you already own" — Netlify). Public search results for a taken domain just say "Unavailable"/"already taken" and pivot to alternatives (verified live on Shopify and Hostinger); no platform claims to know whether the searcher is the owner — ownership language is always conditional ("If you already own a domain... you can connect it") and actual verification happens later via a TXT record, or implicitly by the user logging into their registrar through Entri/Domain Connect. Where both connect and transfer exist, connect is the fast default for novices (minutes–48h, free, no risk) and transfer is sold on consolidation ("manage everything in one place") but carries disclosures every UX must make: ICANN 60-day locks, 5–20 day duration, unlock + auth/EPP code, mandatory 1-year renewal purchase, and an approval email. Squarespace is the outlier that actively recommends transfer; Shopify/Wix/WordPress.com frame it as a neutral preference-based choice.

## technical-detection

SUMMARY
Real-time detection is highly feasible: for gTLDs (.com etc.), a single RDAP query to the registry (e.g. rdap.verisign.com) returns in one round trip either 404 (domain not in registry, i.e. almost certainly available) or a structured JSON record that always includes the sponsoring registrar's name and IANA ID — registrar identity is registry-level data and is NOT hidden by WHOIS privacy, so "Registered at GoDaddy" is reliable for gTLDs (but ~40% of ccTLDs incl. .de/.uk/.jp are still WHOIS-only text blobs). Production search-as-you-type (Instant Domain Search, Domainr) is built on nightly zone-file indexes plus live registry confirmation, with ~300ms debounce, request cancellation, and checks fired only once the string parses to a valid registrable domain; DNS NXDOMAIN alone is a fast but false-positive-prone availability signal. Domain Connect support IS detectable before the user clicks — a millisecond DNS TXT query for _domainconnect.{domain} plus a settings GET tells you whether one-click DNS setup will work; supported DNS providers today are GoDaddy, Cloudflare, IONOS, NameSilo, Plesk, Vercel, WordPress.com, Squarespace Domains (not Namecheap), and Shopify productizes exactly this as a "Connect automatically" button shown only for Cloudflare/GoDaddy/IONOS. For same-platform collisions, Squarespace and Wix show "already connected to another site" with a self-serve move/reassign flow (Wix: "Redirect it to the primary domain" vs "Replace the current primary domain"), while Shopify dead-ends users into contacting support — a documented pain point to avoid. Edge inputs have standard handling: strip URL scheme/path/www, extract registrable domain via the Public Suffix List (handles subdomains and co.uk correctly), validate the TLD against the IANA root list (1,437 delegated TLDs), punycode IDNs via UTS-46, enforce RFC 1035 length limits (63/253), treat spaces/no-TLD input as a name-generation seed, and map registry premium status (EPP fee extension / Domainr "premium") plus aftermarket statuses to plain "taken" since DreamHost has no brokerage. TLD typo correction (".con" → ".com") has a solid precedent in mailcheck.js (Levenshtein against a known-TLD list) though no major registrar search field verifiably does it today.

FACTS
- [verified] ICANN sunset WHOIS for gTLDs on January 28, 2025; RDAP is now the authoritative registration-data protocol for all gTLDs, so every .com/.net/.org/new-gTLD registry must run an RDAP server.  (https://www.icann.org/en/announcements/details/icann-update-launching-rdap-sunsetting-whois-27-01-2025-en)
- [verified] Verisign's RDAP endpoint for .com is https://rdap.verisign.com/com/v1/domain/{domain}; a 404 means the domain 'does not exist in the registry' (RFC 7480) and the response body is empty; both Unicode and punycode IDN forms are accepted; case-insensitive.  (https://rdapapi.io/blog/verisign-rdap-endpoint)
- [verified] RDAP 404 is NOT a perfect 'available to buy' signal: reserved names, registry premium names, and client-side errors (querying a subdomain, trailing dots, TLD mismatch in the path) all complicate it — a final authoritative check (registrar/EPP) is needed before purchase.  (https://rdapapi.io/blog/verisign-rdap-endpoint)
- [verified] Verisign does not publish RDAP rate-limit thresholds; the standard mechanism is HTTP 429 Too Many Requests with a Retry-After header (RFC 7480 §5.5), so production availability checking needs backoff, caching, and 429 handling.  (https://rdapapi.io/blog/verisign-rdap-endpoint)
- [verified] rdap.org is a bootstrap redirector (302-redirects each query to the authoritative RDAP server per the IANA bootstrap registry) but is rate-limited to 10 requests per 10 seconds via Cloudflare — unsuitable as a production backend for search-as-you-type; high-volume clients should consume IANA bootstrap files directly.  (https://about.rdap.org/)
- [likely] Roughly 60% of ccTLDs have deployed RDAP (a 12% increase since January 2025); major ccTLDs including .de, .uk, .cn, .jp, .ca, .au still answer only over WHOIS, so registrar detection there requires parsing unstructured WHOIS text. - [verified] WHOIS port-43 rate limits are opaque and harsh: some registries tolerate a few dozen queries per minute, others block after 2-3 requests, with blocks lasting minutes to 24 hours — a key reason live search fields avoid WHOIS.  (https://rdapapi.io/blog/whois-rate-limits)
- [verified] In RDAP responses the registrar name and registrar IANA ID are always public and structured (an 'entity' with role 'registrar'); WHOIS/GDPR privacy redaction removes registrant contact fields only, never the registrar — so 'At GoDaddy' can be stated reliably for any gTLD. - [verified] Verisign runs a thin registry: its RDAP response contains registrar sponsorship, nameservers, dates, and EPP status codes — no registrant contacts (those live at the registrar). - Only claim a specific registrar when RDAP returns one (all gTLDs); for WHOIS-only ccTLDs (.de, .uk, .ca, .jp, .au) or parse failures, degrade to neutral copy like 'registered with another provider' rather than guessing — registrar name is never privacy-redacted on gTLDs, so a wrong guess would be an implementation bug, not a privacy artifact.
- Never dead-end the same-platform collision: adopt the Wix/Squarespace self-serve pattern ('already connected to your site X — move it here?' with explicit redirect-vs-replace choices), not Shopify's contact-support flow, which generates years of community complaint threads.
- Treat every non-domain input as intent, not error: strip scheme/path/www silently (show the normalized domain back), reduce subdomains to eTLD+1 via the Public Suffix List while remembering the subdomain for the connect flow, and route spaces or TLD-less phrases ('coffee roasters') straight into AI name generation — the field should have no dead 'invalid input' state except gibberish TLDs, where a mailcheck-style Levenshtein 'Did you mean .com?' is cheap because TLD validation against the 1,437-entry IANA list already happens.
- Map registry 'premium' status (detected via fee-extension pricing at check time) and all aftermarket statuses (marketed/priced/transferable) to a plain 'taken' presentation with alternatives, since DreamHost has no brokerage — do not surface aftermarket price or 'make an offer' affordances.
- Do not build live search on rdap.org (10 req/10s) or raw WHOIS (opaque bans); use registry RDAP directly with IANA bootstrap, cache aggressively, and consider a zone-file index (Instant Domain Search model) if per-keystroke coverage across many TLDs is desired — biasing errors so a name is never shown as taken when it is available.
- Design the 'available' state to survive the 404-isn't-a-promise gap: keep search-time price 'indicative' and re-verify availability + price when the user commits (GoDaddy's definitive-flag + registration-quote pattern), with graceful copy if the name was sniped in between.
